### Checked, not changed

**Finding 3 (RLS)** was probed read-only against the linked project
(`bdptplvksniheaqjitek`). All four migrations are applied on the remote, and
every table returns zero rows to the anon key — including `audit_log` and
`deletion_requests`, which have no client policy at all. That is the signature
of RLS being **on and enforcing**.

So the permissive-drift scenario is ruled out — no child's save is exposed.
The other branch is confirmed instead: with `auth.uid()` always NULL, the
game's direct table access cannot work. Concretely, as deployed:

- `loadGameState` selects zero rows → every session starts from scratch
- `saveGameState` upserts fail → "Couldn't save to the cloud"
- `searchUsername` (the "I'm on a new device" flow) can never find an account
- friends and gift reads always come back empty
- `username_pool` is unseeded, so the signup suggestion chips are empty —
  cosmetic only, since the Edge Function stopped requiring the pool

This needs the Edge Function or real-JWT decision from finding 3. Not touched,
because the fix changes how every save works and that is your call.

### Still open

Findings 4 (service-role key in a client bundle), 5 (903 MB of review art in

as an unfinished feature rather than dead code, and it is still there. Either
wire it into `SocialScene` or delete it deliberately.

means rewriting `/assets/animals/*.png` paths across ~10 TypeScript sites and
a dozen admin HTML overlays, with silent broken images as the failure mode. In
a side-by-side trial PNG palette quantisation at q90 recovered 69% against
WebP's 86% — most of the win, no path changes at all — so that is what was
applied, in place, via `tools/optimise-sprites.ts`. WebP remains available as
a follow-up worth roughly another 17 MB.

## Verdict

The logic layer is in good order: typecheck clean across all five packages,
build clean, 901 unit tests, two TODO markers in ~44k LOC, and a child-privacy
schema that is genuinely careful and test-enforced. The problems are all at the
edges — what gets shipped to the browser, and whether saved games actually
persist.

Three things would stop this being playable by a real child on a real iPad:
the service worker tries to precache 454 MB, the loading screen gates on
100 MB, and the Supabase row-level-security policies cannot match the way the
game authenticates.

## P0 — Blocks shipping

### 1. Service worker precaches 454 MB

From the build log:

```
precache  1124 entries (465522.88 KiB)
```

`vite.config.ts` sets `globPatterns: ['**/*.{js,css,html,png,jpg,svg,woff2}']`
over the whole of `dist/`. `globIgnores` excludes `regen-v3-sprites`,
`cast/original`, `reference`, `samples` and the preview folders — but **not**
`admin/scene-assets` (158 MB precached) or `admin/vehicle-restyle`.

Consequence: on first visit the SW attempts to download and cache 454 MB. iOS
Safari's per-origin cache quota is far below that, so `install` fails, the SW
never activates, offline mode never works, and the whole download is retried on
every visit.

**Fix:** add `**/admin/**` to `globIgnores`, then move the handful of files the
game genuinely needs at runtime out of `/admin/` and into `/assets/`:

- `admin/scene-assets/cast/*.png` + `cast/variants/*` (dialogue portraits)
- `admin/scene-assets/cast/apprentices/*`
- `admin/scene-assets/birchie-map/birchie-roads.svg` (the GPS map)

### 2. Loading screen gates on 100 MB

Measured from the asset manifest, using `AssetLoader.parseEntry`'s own tiering
rules:

| Tier | Files | Bytes |
|---|---|---|
| boot | 5 | 1.1 MB |
| **essential** (loading screen waits on this) | **439** | **100.4 MB** |
| variant (background) | 449 | 138.4 MB |

`assets/` totals 239 MB, of which `animals/` is 143.7 MB, `driving/` 40.2 MB,
`bg/` 31.9 MB, `audio/` 20.2 MB.

**Fix:** see finding 12 — most of this is recoverable without touching the art
direction.

### 3. RLS policies cannot match the auth model

The game talks to Supabase two ways:

- Edge Functions for `signup`, `login`, `add-friend`, `send-gift`,
  `claim-gift`, `create-showcase`, `get-showcase`, `get-pin-hint`
- **Direct table access with the anon key** for `game_states`
  ([loadSaveState.ts:69](../apps/game/src/game-state/loadSaveState.ts#L69),
  [:289](../apps/game/src/game-state/loadSaveState.ts#L289)), `users`,
  `username_pool`, `friendships`, `gifts`, `rescue_stats`

The login Edge Function returns a random 32-byte hex string
(`_shared/crypto.ts:62`), not a Supabase JWT, and nothing ever calls
`supabase.auth.setSession()`. So on every direct table call `auth.uid()` is
NULL — while `00002_rls_policies.sql` keys every policy except
`username_pool_read` and `showcase_read_public` on `auth.uid()`.

Two possibilities, both serious:

- **Policies are live as written.** `select` under RLS filters rows rather than
  erroring, so `loadGameState` returns zero rows, is treated as a first-time
  player, and the child starts from scratch every session. `saveGameState`'s
  upsert fails and shows "Couldn't save to the cloud".
- **Live policies have drifted permissive.** Then any anonymous client with the
  public anon key can read or overwrite any child's saved game by `user_id`.

**Verify first**, before changing anything:

```sql
select tablename, rowsecurity from pg_tables where schemaname = 'public';
select tablename, policyname, qual from pg_policies where schemaname = 'public';
```

**Then fix** one of two ways: route saves through a `save-game` / `load-game`
Edge Function like the rest of the auth surface (consistent, minimal change to
the policies), or issue a real Supabase JWT at login so `auth.uid()` resolves.

### 4. Service-role key wired into a client bundle

`.env.local` holds `VITE_SUPABASE_SERVICE_ROLE_KEY` and `VITE_ADMIN_PASSWORD`.
`apps/admin/src/main.tsx:14` reads the service-role key via `import.meta.env` —
the `VITE_` prefix means Vite inlines it into the JavaScript bundle.

Currently not exposed: `vercel.json` builds only `@arc/game`, and neither
secret appears in `apps/game/dist` or `apps/admin/dist`. But one `vercel
deploy` from `apps/admin` publishes a key that bypasses RLS entirely. The
client-side `VITE_ADMIN_PASSWORD` check is also bypassable by anyone who opens
devtools.

**Fix:** drop the `VITE_` prefix, move admin reads behind an Edge Function with
the service role held server-side, or keep `apps/admin` explicitly local-only
and document that it must never be deployed.

### 5. 903 MB of review artefacts committed and deployed

`apps/game/public/admin/` holds 984 MB on disk, 903 MB of it tracked in git:

| Folder | Size | Tracked files |
|---|---|---|
| `regen-v3-sprites/` | 640 MB | 419 |
| `scene-assets/` | 261 MB | 289 |
| `vehicle-restyle/` | 81 MB | 0 (gitignored) |

`.git` is 1.3 GB; `dist/` is 1.1 GB, of which `dist/admin` is 915 MB. Every
clone, every CI run, and every Vercel deploy carries this.

**Fix:** move `regen-v3-sprites/` and the review sheets out of `public/` into an
untracked `asset-drafts/` sibling (the pattern already exists and is already
gitignored). History rewrite is optional — stopping the growth matters more.

### 6. `FriendsScene` is dead code

### 7. `TunnelScene` is never run

### 8. `PtvDriveScene` is unreachable from the game

|---|---|---|
| `packages/*` logic | 9,868 | 786 |
| `game/driving` | 1,851 | 115 |
| `game/scenes` | 14,652 | none |
| `game/game-views` | 4,483 | none |

### 10. One failing test — timezone-dependent

```
FAIL src/__tests__/calendar.test.ts > isDailyReset > returns false when still on the same real day
```

`formatDateYMD` (`calendar.ts:266`) reads local date parts; the fixture uses
`new Date('2026-01-01T23:59:59Z')`. In any timezone east of UTC that instant is
already the next local day. Fails on this machine right now (CEST). The
implementation is arguably correct — daily reset should follow the player's
local midnight — so fix the test, not the function: build the fixture from
local parts, or pin `TZ=UTC` in the vitest config.

## Animal sprites

523 files, 143.7 MB, average 281 KB. Cross-checked against
`SPECIES_VARIANTS` × the 10 states in `AssetLoader.ANIMAL_STATES`.

### 11. 68 sprites missing — hedgehog has no art at all

- **Hedgehog: 61 missing.** All 6 variants × 10 states, plus
  `hedgehog-playing.png`. The logic is fully wired — `hedgehog.test.ts` pins an
  11-point cross-module contract across walks, food, facts, crates, toys,
  wardrobe, garden temperament, habitat and rain tolerance — but no variant art
  exists. It unlocks at level 7, so the last species a child earns is the only
  one where all six "different character designs" render identically.
- **`{species}-playing.png` missing for all 8 species.** The species-level
  fallback for the play minigame. `getAnimalTextureKey` degrades to
  `-sheltered`, so nothing breaks — the animal just sits in the wrong pose
  until the variant tier finishes loading.

### 12. The `-playing` sprites are 44% of the animal payload

| State | Files | Total | Avg |
|---|---|---|---|
| **playing** | 44 | **63.7 MB** | **1,483 KB** |
| growling | 52 | 10.2 MB | 201 KB |
| arriving | 52 | 9.4 MB | 186 KB |
| grumpy | 52 | 9.1 MB | 179 KB |
| scared | 52 | 9.1 MB | 178 KB |
| sleeping | 52 | 9.0 MB | 178 KB |
| sick | 52 | 8.3 MB | 163 KB |

43 files are 1024×1024; everything else is 512×512. Dimension histogram across
the folder: 512² ×407, 128² ×70, 1024² ×43, 256² ×2, and one 103×129.

Resizing the 1024s to 512 recovers roughly 55 MB on its own. Converting the
whole folder to WebP would take another large bite — these are displayed at
~128 px.

### 13. `createAnimalSprite` renders every animal at 2× its requested box

`ui/sprites.ts:88`:

```ts
const scale = Math.min(w / img.width, h / img.height) * 2; // 2x because sprites are 128px
```

Sprites are no longer 128 px, and because they are square the `min()` always
resolves to the smaller dimension — so the rendered size is exactly twice the
requested box, whatever the source resolution. A caller asking for
`{ width: 80, height: 64 }` gets a 128×128 image: 60% wider and 100% taller
than the box it was given. `RoomView`, `GardenView`, `WalkScene`, `PlayScene`
and the picker views all pass explicit sizes that are being silently doubled.

Worth checking against the layouts before changing — some spacing may have been
tuned around the doubling.

### 14. The `sick` state is drawn for every animal and never used

52 sprites, 8.3 MB. `deriveVisualState` only ever returns `arriving`,
`sleeping`, `eating` or `sheltered`, and no caller passes
`stateOverride: 'sick'` — the only overrides in the codebase are `sheltered`,
`walking`, `playing`, and the conflict pair. Sickness is tracked properly in
`store.sickAnimals` and drives the vet flow, but a sick animal looks identical
to a well one.

Cheap win: return `'sick'` from `deriveVisualState` when the animal is in
`sickAnimals`. The art is already on disk and already downloaded.

### 15. Orphaned sprites

Not reachable from the species catalogue:

- `raccoon-walking.png`, `skunk-walking.png` — species not in `Species`
- `cat-scarf`, `bunny-scarf`, `bat-scarf`, `dog-coat`, `fox-coat`,
  `parrot-hat`, `snake-hat` — wardrobe garments; note these land in the
  *variant* tier because `parseEntry` only treats a two-token name as
  essential when the second token is a known state, so an equipped garment
  won't render until the background tier lands
- `dog-golden-sheltered-body.png`, `dog-golden-sheltered-tail.png` — a layered
  rig experiment

## Map and driving

### 16. Two competing coordinate systems, one of them dead

`destinations.ts` gives all 9 destinations a `mapX` / `mapY` on a 0–100 grid,
and `destinations.test.ts` asserts they are in range. Nothing renders them —
there is not a single read of `mapX` anywhere in `apps/` or `packages/`.

The real positions live in `driving/birchie-places.ts` as map fractions. So the
test passes, gives confidence, and guards data no code uses. Either delete
`mapX`/`mapY` and its test, or make `birchie-places.ts` the single source and
derive from it.

### 17. Two destination pins sit well off the road network

`birchie-places.ts` flags itself as provisional. Measured distance from each pin
to the nearest node in the road graph (map fractions; 0.01 ≈ 18 px on the
1800 px map):

| Place | Snap distance | ≈ px |
|---|---|---|
| bramble-farm | 0.0703 | 127 |
| cove-harbour | 0.0667 | 120 |
| moorland | 0.0450 | 81 |
| woodland | 0.0346 | 62 |
| deep-forest | 0.0333 | 60 |
| sea-cliffs | 0.0276 | 50 |
| pinebark-medical | 0.0109 | 20 |
| wetlands | 0.0035 | 6 |
| arc | 0.0016 | 3 |

The three speed cameras are all within 0.006 — those are well placed. But
bramble-farm and cove-harbour are ~7% of the map width from the nearest road,
so the GPS route line visibly starts or ends in open country.

### 18. Road graph is sound

2,211 nodes, 2,475 edges, 5 connected components. The main component holds
2,123 nodes and **every destination and camera snaps into it**, so Dijkstra
always finds a real road route and the straight-line fallback never fires. The
four orphan islands (42, 38, 6 and 2 nodes) are unreachable dead data — harmless,
worth pruning when the graph is next regenerated from `birchie-roads.svg`.

## What's genuinely good

Worth recording, because an audit that only lists problems misrepresents the
codebase:

- Typecheck clean across all five packages. Build clean. 901 tests passing (the
  one failure is environmental).
- Two TODO markers in ~44k LOC.
- The privacy schema is careful and enforced: no email except a hashed parent
  address, no age, no date of birth, no location, no free-text fields, preset
  message codes for gifts — and `privacy-audit.test.ts` reads the migration
  files and fails if any of that regresses.
- Auth is server-side in Edge Functions, with PIN hashing, rate limiting and
  real error bodies plumbed through to the child-facing copy.
- The asset loader's three-tier design, its batching around Phaser's
  32-parallel-download cap, and the sprite fallback chain are all well
  reasoned — and the reasoning is written down in the comments where it will
  still be readable in a year.
