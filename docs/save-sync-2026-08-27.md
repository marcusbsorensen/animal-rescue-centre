# Save sync, phase 1 — 27 August 2026

Groundwork for one account across iPad, iPhone and the web. This phase makes
a save survive a bad connection and makes a collision between two devices
*visible*. It does not decide who wins a collision — that is phase 2.

## What was wrong

Two defects, both silent.

**No local copy at all.** `saveGameState` posted to an Edge Function and, if
that failed, showed a toast and dropped the snapshot. Not localStorage, not
IndexedDB, nothing. An afternoon played on a train existed nowhere.

**No conflict detection.** `save-game` wrote `game_states` with a blind
`upsert`. Two devices on one account meant whichever saved last erased
whatever the other had done since, and nothing anywhere recorded that it had
happened. `updated_at` was no help: it says when a write landed, not what the
writer believed it was replacing.

## What phase 1 does

### `version` on `game_states`

`00006_game_state_version.sql` adds `version bigint not null default 0` and a
`BEFORE UPDATE` trigger that owns both `version` and `updated_at`.

Server-owned deliberately. A caller-supplied version could be set to anything,
which defeats the point of having one; a caller-supplied timestamp is a clock
we do not control. The trigger takes both out of the request.

Existing rows start at 0, which is also what a client that has just loaded an
un-versioned row will send — so the migration itself locks nobody out.

### Conditional writes in `save-game`

The request carries `expectedVersion`, and it has three meanings:

| `expectedVersion` | Means | Behaviour |
|---|---|---|
| a number | "I loaded this version and expect to replace it" | `update … where user_id = … and version = …`. No match → 409. |
| `null` | "I don't believe there is a server row" | insert only. Row already there → 409. |
| absent | a client running JS cached from before this shipped | old blind upsert |

The legacy path is deliberate. Refusing an unversioned write would lock a
child out of saving until their service worker updated, which is a worse
failure than the last-write-wins they have always had. The trigger still moves
the version on, so a *new* client holding the previous one finds out.

The normal path is one statement — the filter and the write are the same
operation, so two devices racing cannot both succeed.

A 409 carries the current server state, not just "no". Without it the only
recovery is a reload, and a reload right after a rejected save is exactly when
a child's last few minutes disappear.

### Local-first writes

`apps/game/src/game-state/localSave.ts`. IndexedDB, keyed by user id.

IndexedDB rather than localStorage for two reasons: a shelter with fifty
animals is comfortably past localStorage's ~5 MB, and localStorage writes
block the main thread — on a save-on-every-interaction game that is a stutter
a child can feel.

Keyed by user id because a family iPad has several children on it.

Nothing in that module throws. Private mode, storage disabled, quota
exhausted — all degrade to "no local copy", which is where the game already
was. A local-save failure must never be the reason a save does not reach the
cloud.

Two records per player: the live snapshot, and — under a `::rejected` key —
the server state a rejected save was told about.

### What the client does now

**Save.** Write to IndexedDB, then post. On success, record the new version
and mark the local copy synced. On a 409: keep the server's copy under the
rejected key, adopt the version it reported, and re-send once.

**Load.** Cloud first. On success, seed the local copy — *unless* this device
is holding an unsynced save, which is left alone because overwriting it would
throw away whatever was played offline. On failure, open the local copy and
carry on with a toast; the blocking retry overlay now appears only when there
is nothing on the device either.

## What phase 1 deliberately does not do

The re-send after a 409 means the newest write still wins — the rule that was
agreed — but bluntly, at the granularity of one save. Nothing is merged, and
the child is not told their two devices disagreed. What is different from
before is that the losing half is on the device rather than gone.

Phase 2 has everything it needs: `getRejectedSave(userId)` holds the other
device's shelter, and an unsynced local save is left in place across a load
rather than overwritten.

Open questions for it:

- Merge, or pick? A shelter is mostly additive — animals rescued, badges
  earned — so a union is plausible for most of the state and wrong for the
  economy.
- What does a child see? "Your shelter looks different on this iPad" is true
  and useless. Probably nothing, if the merge is good enough.
- The unsynced-local-vs-newer-cloud case on load is currently resolved in the
  cloud's favour for the *store* while the local copy is preserved on disk.
  That is a holding position, not an answer.

Typecheck, lint (0 errors), 941 unit tests including 21 new ones covering the
version plumbing and the local store, production build, and the e2e scene walk
